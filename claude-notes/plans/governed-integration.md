# FHEM, radio signals and the "governed" integration (PROJECT.md 37)

Started 2026-11-08 from Erik's discussion (recorded in PROJECT.md 37). Planning.
Decided (Erik, 2026-11-08): the integration is called **governed** (it was "indirect" in the
discussion); sending a signal is written "on by doing <button>", so it reads as an action.

## The distinction

Both FHEM radios are in scope (Erik, 2026-11-08): FS20 and DuoFern. FS20 is one-way (below), so
it is case 2. DuoFern (Rademacher) is a cover system, reached through FHEM with a dongle and not
(yet) supported by Home Assistant itself (Erik); it acknowledges commands (FHEM2MQTT brief,
below), so it is case 1 -- a FHEM sub-integration for covers, no enforcing needed.

1. **Devices with a reliable two-way connection** (a real light or switch that reports its own
   state). FHEM's syntax for these differs per platform behind it, so FHEM gets sub-integrations,
   in the shape of the Shelly layer: a statement inside a device implies its topics and metadata
   from a family table (claude-notes/plans/shelly-layer.md).
2. **Devices we only reach by radio** -- FS20 first, but also IR and Bluetooth -- with at most an
   indirect report of their state, from some other device. For these:
   - an **outgoing** radio signal is a **button** capability with a value (on, off, 50%);
   - an **incoming** radio signal is an **event** capability;
   - a new **governed integration** (Physical layer) defines the device itself: its metadata, and
     its state, controlled through those buttons and, where possible, corrected from sensors or
     events. The buttons, sensors and events may come from any integration.

## FS20 facts (FHEM's own module, 10_FS20.pm, read 2026-11-08)

- **Actuators send nothing back.** FHEM only ever transmits in `FS20_Set`; there is no
  acknowledgement or status handling, and the module notes "The FS20ST ... does not respond to
  sendstate". The FHEM wiki: FS20 has no return channel ("fehlender Rückkanal"). Switching an
  actuator by hand on the device is not seen at all.
- **Transmitters are seen.** A remote or wall switch (S4, S20, ...) sends the same frames as FHEM
  does; `FS20_Parse` updates the state of every defined device with the same housecode and
  button. So FHEM sees a *transition someone asked for* on the radio -- not whether the actuator
  received it.
- **Dim levels**: 16 steps, `dim06%` .. `dim100%` (6, 12, 18, 25, 31, 37, 43, 50, 56, 62, 68, 75,
  81, 87, 93, 100), `off` for 0, `on` back to the previous level. FHEM itself does not round:
  `set <dev> dim 40` fails, only the 16 values are accepted. Also `toggle`, `dimup`, `dimdown`,
  `on-for-timer`/`off-for-timer <s>` (rounded up to one of 112 durations, at most 15360 s).
- **Duty cycle**: 868 MHz is a 1 % band; a CUL has `credit10ms`, and refuses to send ("LOVF") when
  it runs out. One frame takes about 0.22 s.

## The earlier FHEM2MQTT brief

Erik's FHEM2MQTT project brief (before this project took FHEM up; the file was removed
2026-11-13, once what matters of it was here) designed the same thing as a separate project. What
carries over, and where it differs:

| Brief | Here |
|---|---|
| Coordinator (generic: routing, re-assertion, HA exposure) | the governed application (re-assertion, the governed entities); routing is MQTT itself |
| Radio Talker, one per FHEM installation, the only platform-specific runtime | no relay: generated FHEM configuration, FHEM's own MQTT (question 6) |
| Configurator (spec -> deployed talkers, SSH, ACLs) | the generator and the deploy, as for every integration |
| HA MQTT Discovery | the generator's YAML `mqtt:` entities (Architecture.md §6.16, since PROJECT.md 19) |
| `requires_periodic_reassert` flag per device | a device of the governed integration, "enforced every X" |

Kept from the brief, as design points for the governed application:

- **Why enforce**: FS20 "silently defaults to off on power loss" -- no event for that ever
  reaches anyone, so only a timer helps.
- **No crossing signals**: per device one *pending command* slot instead of a queue (a newer
  command replaces an untransmitted older one), and a sequence number so a stale command -- or a
  retry of one -- is dropped. Enforcing goes through the same slot, so a real command always
  pre-empts an enforcement tick.
- **Stagger** enforcement across devices (FS20 has no collision detection), and keep it inside the
  radio's duty cycle -- the throttle groups.
- **One command topic per device**, the state as payload (MQTT keeps order only per topic);
  command topics not retained (a retained command replays to every new subscriber); state topics
  retained.
- **Interval**: the brief starts at about 60 s; the old FHEM generator used 5 minutes.
- **Optimistic** in Home Assistant for an entity whose state is assumed, not observed.

Also from the brief, added 2026-11-13 (for DuoFern and later):

- **A device that acknowledges needs none of this**: DuoFern confirms each command and reports its
  own state, so it is not enforced and not optimistic -- case 1, its state is observed.
- **Commands live-only**: a command must not wait while FHEM is briefly offline and replay on its
  reconnect; the brief leaned towards clean sessions for command subscriptions, or MQTT 5's
  message expiry (a few seconds) as a broker-side safety net. Still to check for FHEM's
  MQTT2_CLIENT.
- **Per-installation broker credentials**, scoped by the broker's ACL to the installation's own
  topics, instead of one shared login (FHEM uses the house's today).
- **Availability per bridge** through its retained last will: here `fhem/installation/<host>`.
- **Platform modules** compiled in, not loaded as plugins (Go's plugin package is Linux-only and
  fragile): here the kind tables (`fhemSerialKinds`, `fs20Kinds`) in the generator.
- Parked in the brief: emulating ESPHome's native API instead of MQTT -- alpha-quality prior art,
  Python only, and no cover entities (needed for DuoFern). And its longer-term ambition: a Home
  Assistant add-on for legacy radios, of which FHEM is only the first platform.

## The governed integration

- **Optimistic state**: the device's state is the one last asked for.
- **Enforced every X**: that assumed state is sent again, through its buttons, every X.
- **State confirmation**: a sensor or event of another device that observes the real state (e.g.
  a plug's power). It updates the governed device's internal shadow state; a discrepancy with the
  desired state leads at once to enforcing the desired state.
- **Its own application**, the *governor*, next to the coordinator: it is operational, not
  coordinative (PROJECT.md 37's 2026-09-22 decision), so it is held to a higher reliability bar and
  is a program and systemd service of its own. It runs on the coordinator's machine (Erik,
  2026-11-08), but the coordinator can be down without it noticing, and the other way around.

- **A transition seen on the radio** (a remote or wall switch sending to the same address, as FHEM
  reports it) changes the *desired* state: someone asked for it. It is not a confirmation that the
  device follows, and must not be enforced back to the old state.

## Example, as Erik describes it

The FHEM integration defines a button that makes every known FHEM installation listen on its topic
and send the FS20 signal; the governed integration builds a switch on it. A sketch only -- every
keyword here is open:

```
integration fhem with:
  ...the installations (part 1)...
  device radio.living_room_lamp with:      # an FS20 address, nothing more
    fs20 "1234" "01";                       # house code, device address
    capability button.on with value "on";
    capability button.off with value "off";
  end;
end;

integration governed with:
  device lights.living_room_lamp with:
    manufacturer: "ELV";
    model:        "FS20 ST-4";
    capability switch.switch
      on by doing button.on from radio.living_room_lamp
      off by doing button.off from radio.living_room_lamp
      enforced every 00:30:00
      confirmed by sensor.power from switches.living_room_lamp_plug above 5;
  end;
end;
```

Home Assistant then sees one ordinary switch, `switch.<position>`, whose state is the governed
application's -- not the buttons.

## Building the governor (started 2026-11-08)

In steps, each tested and deployed before the next:

1. The governor (`governor/`, a Go program of this repository): for a governed switch, the desired
   state retained on the broker (`governed/<device>/<label>`, commands on `.../set`), the default
   when nothing is retained, enforcing every X, the throttle per radio channel (a token bucket:
   a frame's time per command, refilled at the duty cycle, holding an hour's worth -- 36 s for
   FS20; since 2026-11-13, when 3 s and a frame per installation held commands back 44 s each), a pending slot
   per entity (a real command before an enforcement), radio-requested changes, and the echoes of
   its own sends ignored. Its liveness: `governed/status`, `online`/`offline` (last will).
2. `integration governed` in the generator: `governor/devices.yaml` and `secrets.yaml`, and the
   Home Assistant entity, as a raw-MQTT capability on the governor's topics (positioning, frozen
   ids and YAML entities stay the generic machinery's).
3. The deploy part `governor`, on the coordinator's machine, like the coordinator's.
4. The dimmer as a light (brightness 0..100, `on at <n> %`) -- built 2026-11-08; then
   confirmations (the shadow state) and the de-doubled transmitters and sensors. An FS20 remote is
   a set of buttons (Erik, 2026-11-08): an FS20 `transmitter`, its presses event capabilities
   positioned like the Zigbee and Philips buttons, and dimming -- of an FS20 light or a Hue one --
   is stepwise, by rules in Conceptual.def through Home Assistant main ("dim"/"brighten"), as the
   Zigbee dimmers do. A remote that sends dimup/dimdown
   while a button is held keeps them as event types of their own -- no eventMap folds them into
   on/off any more -- and the rules deal with them, as with the Philips dimmer remote. So the
   governor never needs a remote's relative dim up/down; heard on a
   governed dimmer's own address it says no level, and is not taken.

Steps 1-3 built and deployed 2026-11-08: the governor on Junglinster's protocols-server-1, the
test switch switched from Home Assistant through both FHEM installations.

## Syntax proposal (2026-11-08, for Erik to judge)

Built on the decisions below (questions 1-7). Two integrations, both in Physical.def.

**1. The FHEM installations**, inside `integration fhem` (agreed, Erik 2026-11-08): a block per
installation, named by its host, with a line per serial device -- its kind and its full path, as
FHEM takes it (`"COM3"` on Windows):

```
integration fhem with:
  installation protocols-server-2 with:
    cul "/dev/serial/by-id/usb-busware.de_CUL868-if00";
  end;
  installation protocols-server-3 with:
    fhz "/dev/serial/by-id/usb-ELV_AG_ELV_FHZ_1000_PC_ELTLYOUK-if00-port0";
  end;
  ...the devices (part 2)...
end;
```

A kind (`cul`, `fhz`, later `duofern`, ...) comes from a table in the generator: the FHEM module
that defines it and the radio channels it serves (a CUL and an FHZ both serve FS20). The generator
writes each installation's whole `fhem.cfg` (question 6); the deploy puts it there. `heard by`
names installations, and is checked: an FS20 device heard by an installation without an FS20
stick is an error. The radio channel's budget is a hard-wired default per channel (FS20: 1 %
duty cycle), which a def may override (keyword open).

**2. The radio side: `integration fhem`**, a layer of the Shelly shape: one statement implies
the topics (`fhem/fs20/<device>`, `.../set`), the capabilities' details and the metadata
("ELV"); the capabilities stay listed.

```
integration fhem with:
  ...the installations (part 1)...
  device radio.living_room_lamp with:
    fs20 dimmer "1234" "01" heard by protocols-server-2, protocols-server-3;    # house code, address; its installations
    capability button.set;                            # takes 0..100, sent as the nearest dim level
  end;
  device radio.hallway_lamp with:
    fs20 switch "1234" "02" heard by protocols-server-2;
    capability button.set;                            # takes on / off
  end;
  device buttons.hallway_remote with:
    fs20 transmitter "1234" "10" heard by protocols-server-2, protocols-server-3;
    capability event.button;                          # types on, off (dim up: on, dim down: off)
  end;
  device sensors.garage_motion with:
    fs20 sensor "1234" "20" heard by protocols-server-3;
    capability binary_sensor.motion;
  end;
end;
```

The four kinds are the old `FS20.Create`'s: `switch`, `dimmer`, `transmitter` (EventPair),
`sensor` (BinarySensor). A `button.set` is never an entity in Home Assistant (question 2's (a)),
and a `radio.*` device is not positioned. A transmitter or sensor is positioned as any device;
Home Assistant reads it from the governed application's de-doubled topic, not from
`fhem/fs20/<device>` -- transparent to the author. DuoFern gets its own statement
(`duofern cover "<code>" heard by ...;`) once its tree is looked at.

**3. The governed side: `integration governed`**, the entities Home Assistant sees:

```
integration governed with:
  device lights.living_room_lamp with:
    manufacturer: "ELV";
    model:        "FS20 DI-20";
    capability light.light
      by doing button.set from radio.living_room_lamp
      enforced every 00:05:00
      default off
      on at 60 %;
  end;
  device lights.hallway_lamp with:
    capability switch.switch
      by doing button.set from radio.hallway_lamp
      enforced every 00:05:00
      confirmed by sensor.power from switches.hallway_plug above 5;
  end;
  device lights.porch_lamp with:
    capability switch.switch
      on by doing button.on from radio.porch_lamp
      off by doing button.off from radio.porch_lamp
      enforced every 00:30:00
      confirmed by event.light from sensors.porch_light
        on "seen_on", off "seen_off";
  end;
end;
```

- `by doing <button> from <device>`: one button that takes the state as its value (question 2).
  `on by doing ... off by doing ...`: a button per state, for radios that have them.
- `enforced every <time>`: resend the desired state, inside the radio channel's budget.
- `default <state>`: overrides the hard-wired default when the broker lost the state (question 5).
- `on at <n> %`: the level a light goes to when it is switched on without one (a dimmer's "on"
  sent as that level, not as FS20's own "on" -- its last level).
- Junglinster's test pair (Erik, 2026-11-08): `radio.test_fs20_switch` and `radio.test_fs20_dimmer`
  (house code 44444444, 4411 and 4412, heard by both installations); their governed entities get
  `default off`, and the dimmer `on at 60 %`.
- `confirmed by <sensor> from <device> above <n>` / `confirmed by <event> from <device> on
  "<type>", off "<type>"`: the source of the shadow state (question 4).
- A received state change on the radio device's topic is taken as radio-requested (question 7):
  implied by `from <device>`, nothing to write.
- The entity's kind gives what it takes: a switch on/off, a light on/off and 0..100, a number
  its range (`number.level ... min 0 max 100`).

## To reflect on (Erik)

- **Throttle groups per radio**: the governed application limits how many requests it sends to one radio.
  For FS20 this is also a legal limit: 868 MHz is a 1 % duty-cycle band, which FHEM's CUL tracks as
  credit. A group is per radio channel (FS20; DuoFern its own), across all sticks, shared by every
  device on that channel (question 7), and enforcement must queue behind it rather than flood it.

3. (decided, Erik 2026-11-08) Definitions: the generator writes them for the governed

   governed application keeps a **shadow state** of what the confirmation source has reported:
   a sensor's value as it is, an event's state from its type, kept until the next report. A
   shadow state that differs from the desired state leads at once to enforcing the desired
   state. Built in from the start, as for a sensor: the project is not for Erik's houses only.
5. (decided, Erik 2026-11-08) The governed state lives on the broker: the retained state topic

   back, then enforces them. A confirmed state, where there is one, on a second retained topic
   (e.g. `<device>/confirmed`). No local file. A device with no retained state (a broker that lost
   them) starts from a default (Erik, 2026-11-08): a hard-wired one per kind of entity, a constant
   in the code (e.g. a switch: off), which the device's definition may override with its own
   default. That state is then enforced like any other.
6. (decided, Erik 2026-11-08: A, as his old scripts did) FHEM is reached through its own MQTT:
   the generator writes FHEM configuration -- per device an `MQTT_DEVICE` listening on the

   publishes what its radio receives (transmitters as events, FS20 sensors as states), as the
   old `EventPair` and `BinarySensor` kinds did. Unlike the old scripts, the generated FHEM
   configuration has no refresh timer (Erik, 2026-11-08): resending is the governed
   application's, which presses the button again; FHEM only sends what it is asked to.

   ASK/OOK and FSK, through remote_transmitter/remote_receiver), used for e.g. Davis weather
   stations and Elero covers, but nothing for FS20 or DuoFern was found. FHEM stays the way in
   (Erik): old hardware -- the CUL sticks and FHZ radios on p-s-2 and p-s-3 -- must remain
   usable. An ESPHome radio could later be one more path to a device, which the governed logic
   already allows (question 7).
7. (decided, Erik 2026-11-08) Several FHEM installations may serve one device, for range, as
   before -- but **each FS20 device lists its FHEM installations**: only those define the device,
   listen on its button topics and send, and publish what their radio receives from it. The
   keyword is open, e.g. `heard by protocols-server-2, protocols-server-3;`. What follows:
   - Duplicate frames: harmless only for absolute commands (`on`, `off`, `dim37%`); the FS20
     layer never sends relative ones (`dimup`, `dimdown`).
   - Throttling is the governed application's (Erik, 2026-11-08): it paces the messages it
     publishes on MQTT to the radios, with one budget per **radio channel** -- e.g. FS20 -- across
     all its radios (sticks): that channel is the throttle group. FHEM is not asked for its
     credit; the sticks only send what reaches them.
   - **FS20 is one "mesh radio"** (Erik, 2026-11-08): all its sticks, in whatever FHEM
     installation, are meshed via MQTT into a single radio. The governed application talks to
     that radio, not to a stick; which sticks a device lists is only its coverage. Its throttle
     group is that one radio; DuoFern is another.
   - **One MQTT topic per FS20 device** (Erik, 2026-11-08): `fhem/fs20/<device>`, used by all the
     FHEM installations that listen and send for that device -- not a topic per installation.
     Split in two (Erik, 2026-11-08), so FHEM never acts on its own output:
     `fhem/fs20/<device>/set` for commands (not retained; only the governed application publishes,
     the FHEMs listen), and `fhem/fs20/<device>` for what the radios receive (only the FHEMs
     publish).
   - **Received radio messages are de-doubled** (Erik): a transmitter or sensor heard by two
     sticks reaches that topic twice, once per FHEM; the copies of one press (the same message
     within a short window) count as one event, or one state change -- the window (Erik,
     2026-11-08, as for the default) a hard-wired one per radio channel in the governor (FS20:
     500 ms), which a device overrides with `copies within <n> ms;` in "integration fhem",
     compared per message, so a held button's repeated dimup/dimdown stay presses. Decided (Erik, 2026-11-08):
     **the governed application does it**, as the radio's one receiver: it reads what the radios
     publish, merges the copies, and publishes the press once for Home Assistant.
   - **The governed logic is neutral about meshing** (Erik, 2026-11-08): messages from and to
     other (kinds of) radios may be combined too. A device is reached through one or more
     *paths*, each a topic set: FS20's sticks share one (meshed via MQTT), other radios may each
     have a topic tree of their own. The governed application sends to every path and merges
     what arrives from all of them, the same way whether there is one path or several.
   - **A stick hears the frames another stick sends** (Erik, 2026-11-08: most likely), and it
     cannot tell them from a remote control's: an FS20 remote sends the same signal to the switch
     and to the sticks. So, for a switch, every state change a stick receives is taken as a
     **radio-requested state change**: FHEM publishes it on the device's topic, and the governed
     application makes it the desired state and reports it up to Home Assistant (if not already
     so). An echo of the application's own command is then simply the state it already has. It
     is **not a confirmation**: it does not touch the shadow state of question 4.
