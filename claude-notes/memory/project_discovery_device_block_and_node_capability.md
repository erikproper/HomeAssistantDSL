generator enforces a real Rule 2 -- a device declaring `battery_level` MUST also declare

Spaces.def device-block entities have NO per-capability icon override syntax yet (unlike

device's old bare-entity custom icon (bitron_thermostat's desktop plug had "mdi:desktop-classic")

Living_room philips_motion + signify_dimmer (2026-09-15) confirmed two more reusable precedents:
a device leaf containing a "/" (`signify/dimmer`, chosen because the leaf's own last segment
wasn't a domain word worth suppressing) produces a purely cosmetic `name:`/`friendly_name:` path
change in already-existing macro-generated files (`signify_dimmer/node` → `signify/dimmer/node`)
while the `unique_id`/entity_id stays byte-identical — expected, not a bug, don't be alarmed by a
node-file diff if that's all it is. Also: pre-existing `battery_alert` files generated by the OLD
`battery_level_device` macro used a bare boolean `state:` expression, while the new `derived`
mechanism emits an explicit `'on' if ... else 'off'` — a cosmetic jinja upgrade, same pattern
already seen migrating the Moes buttons/frient sensors, not a regression.

## Step 1 — find a migration candidate

Look in Spaces.def for either shape, inside a space that still has un-migrated devices:
- a bare `entity <spec>;` with no `from ...;` at all (relies on implicit discovery_passthrough
  matching), or
- a macro call with no matching Physical.def discovery gateway backing it: `call
  battery_level_device :X with alert_level N;`, `call light_device light.social:X;`, `call
  switch_device switch.social:X;` (these ARE just node-registration sugar around a bare entity —
  confirmed live 2026-09-15, hallway light.social:main).

`project_undeclared_entity_audit_technique.md` has a reusable scan for exactly this.

## Step 2 — find the real Zigbee2MQTT identifiers

SSH to the coordinator host and read its own broker directly (credentials/host/port come from that
house's own `coordinator/secrets.yaml`, NOT hardcoded — Vienna's happen to be
`carvalhoproper`/`PaulaErik1967`/port 1883 on localhost once tunnelled via `ssh -p 1970
erikp@vienna.homelinux.org`; Junglinster's own deploy scripts will have its own equivalent, look
there first):

```
ssh -p 1970 erikp@vienna.homelinux.org \
  "timeout 5 mosquitto_sub -h localhost -p 1883 -u <login> -P <password> \
   -t 'homeassistant.physical/+/+/+/config' -v" 2>&1 | grep -i '<room>/<device-name>'
```

From each matching payload, note: `device.identifiers[0]` (the gateway's own `identifiers`, e.g.
`"zigbee2mqtt_0x..."`) and each capability's own `unique_id` (the `leaf`). Watch for a leaf
`unique_id` published under **more than one raw topic domain** (e.g. Z2M's own "sensor" text
mirror + "event" entity sharing one unique_id for a button's "action") — see Step 4's
domain-qualification note.

## Step 3 — name the gateway

`discovery.<room>_<device>` when the same model/name could collide elsewhere in the house (e.g.
`hallway_frient` vs `bedroom_frient`); bare `discovery.<device>` is fine when it's unique
house-wide.

## Step 4 — decide capability labels (Physical.def)

- Exactly one capability is "the device's whole reason for being" (a bulb's light, a switch's
  on/off, a motion sensor's occupancy, a button's action, a contact sensor's open/closed) → label
  it `core`, regardless of whether it also has an intuitive domain-specific name — the deciding
  question is "does this reading alone justify the device existing," not "is there a more specific
  word available" (confirmed 2026-09-15: aqara_windoor's `door` → `core`, frient's `occupancy` →
  `core`).
- Genuine MULTI-peer sensors with no single "more primary" reading (temperature+humidity+pressure,
  or a light+illuminance+temperature+battery combo device) → keep their own real names, no `core`
  invented.
- A capability whose raw MQTT leaf is published under more than one domain for the same
  `unique_id` → qualify it: `<domain>.<label>: <raw-domain>:<leaf>;` (e.g. `event.core:
  event:0x..._action_zigbee2mqtt;`). Omit the qualifier (the common case) when the leaf is
  unambiguous — this is also what lets a capability deliberately relay a leaf published under a
  DIFFERENT raw domain than its own declared one (`fan.core: 0x..._switch_zigbee2mqtt;`).
- A capability needing an arithmetic adjustment with NO native corrected signal from the gateway →
  declare the raw leaf `hidden sensor.X_raw: <leaf>;` and add `derived <domain>.X from sensor.X_raw
  via jinja ${<macro>}(<args>);` (Shared/Settings.def's `jinja ${name}(params) = "template";`
  macros: `int_less_then`/`int_more_then`/`add_float_value`/`scale_float_value`/
  `adjust_float_value` already exist, add more there if a new shape is needed — don't hand-roll
  a "via" string when an existing macro fits).
- A capability the gateway ALREADY computes natively (e.g. Z2M's own `battery_low` boolean) → use
  it directly as a plain leaf, never invent a derived threshold for something already provided.

## Step 5 — the node capability

Always add `binary_sensor.node: <domain>.<sibling-label> is available;` (domain qualifier is
MANDATORY, not inferred — a device could otherwise declare two same-labeled capabilities under
different domains with no way to disambiguate). Anchor on `core` when the device has one;
otherwise anchor on `battery_level` (established precedent for genuine multi-sensors). The node
entity itself is **auto-implied** the moment the device gets positioned in Spaces.def — never write
an explicit `entity binary_sensor....:node from node;` line, it's redundant and produces a
"defined more than once" warning.

## Step 6 — choose the Spaces.def device leaf to preserve existing entity_ids

Before writing anything, work out what the CURRENT (pre-migration) entity_id is for every
capability being migrated (trace through whichever macro or bare declaration produces it today).
Then choose the device positioning leaf (`device infrastructural:<leaf> from discovery.<gateway>
with: ...`) so `namingSpacePath`'s injection reproduces those exact paths:

- Ordinary case: leaf = the same path segment the entities already use (e.g. `frient`, `door`,
  `bedroom/door/moes`).
- When ONE capability's own domain word already says what the device leaf would otherwise repeat
  (a light device whose leaf is itself named after a domain-ish word, e.g. "main/light") —
  `namingSpacePath`'s suppression rule fires when a capability's domain equals EITHER the whole
  device leaf OR just its last "/" segment, letting that ONE capability skip the redundant segment
  while every OTHER capability (e.g. the auto-implied node, which has no domain-based redundancy of
  its own) still gets the full leaf as context. This is what reproduced BOTH
  `light.social_apartment_hallway_main` AND
  `binary_sensor.infrastructural_apartment_hallway_main_light_node` exactly, zero renames at all —
  worth checking for on every light/switch/fan-shaped device migrated off the old
  `light_device`/`switch_device` macros, which always used to hand-append a domain suffix
  ("${entity.path}/light") to the node's own path for exactly this reason.
- For a genuinely NEW capability with no historical entity_id to match (e.g. a button's `core`,
  where the old macro-based form never exposed a press-event entity at all) — free choice, pick
  whatever reads naturally.

A rename IS sometimes unavoidable or even a deliberate improvement (e.g. a hidden capability's own
auto-implied entity_id, which always lands under the DEVICE's own sphere — accept it, it's
internal-only by design) — but always try the leaf choice that avoids one first, and call out any
that remain explicitly rather than let them slip through unnoticed.

## Step 7 — write Physical.def

Inside the existing `integration discovery with: ... end;` block:

```
device discovery.<gateway_id> with:
  identifiers "zigbee2mqtt_<ieee>";
  <domain>.<label>: [<raw-domain>:]<leaf>;
  ...
  binary_sensor.node: <domain>.<anchor-label> is available;
  [derived <domain>.<label> from <domain>.<hidden-label> via jinja ${...}(...);]
end;
```

## Step 8 — write Spaces.def

```
device infrastructural:<leaf> from discovery.<gateway_id> with:
  entity <domain>.<sphere>:<explicit-path> from <label>;
  ...
end;
```

No explicit node line (Step 5). Drop whatever bare/macro form this replaces.

## Step 9 — build, test, regenerate, diff (before touching anything live)

```
cd homeassistant/homeassistant && go build ./... && go vet ./... && go test ./... -count=1 && go install .
cd <House> && cp coordinator/discovery.yaml /tmp/discovery.yaml.before && cp -r hass /tmp/hass.before
./generate   # watch for real warnings, vs. harmless "no cache yet" noise for a brand-new gateway
diff /tmp/discovery.yaml.before coordinator/discovery.yaml
diff -rq /tmp/hass.before hass
```

Confirm the diff shows ONLY the entity_ids you intended to add/change — an unexpected rename means
the deviceNamePath choice (Step 6) was wrong. Spot-check the generated node/derived template
files' own `state:` condition line for correctness.

## Step 10 — deploy and verify live

```
./deploy
```

Then, **every time** (a real incident happened once this session where an edit silently reverted
between an Edit call and the deploy — always re-verify, never assume the earlier Edit result still
holds):
1. `grep` the local Physical.def/Spaces.def one more time to confirm the edit is still there.
2. SSH and check the REMOTE `coordinator/discovery.yaml` line count / `grep -c 'gateway:'` directly
   — never trust "coordinator restarted cleanly" alone (a real incident: a truncated,
   near-empty discovery.yaml reached the coordinator once, dropped the WHOLE house to raw
   passthrough, and the service still started up looking perfectly healthy).
3. `journalctl -u coordinator -S '1 minute ago'` — count `queued relay of` lines (should match the
   expected new entity count), confirm zero real errors (ignore `[paho-WARN] memorystore wiped`,
   and substring false-positives like "...wash_error_code" matching a grep for "error").
4. Optionally `mosquitto_sub` the actual published MQTT discovery config for one new entity, to
   confirm the payload shape (value_template, event_types, brightness/color capabilities, etc.)
   survived the relay intact.

port/login carry over). The Shared/Settings.def jinja macros are already available to it too, since
