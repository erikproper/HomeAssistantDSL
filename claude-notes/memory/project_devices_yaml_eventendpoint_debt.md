Found 2026-08-20: the `cpu/<host>/state` MQTT topic convention was hardcoded independently in
two places — `generateReportingAutomations` (Go) and the deployed `Integrations/cpu/report`
shell script — with no shared source of truth. `coordinator/devices.yaml` (generated by
`integration_hosts_generator.go`) had no `topic:` field at all despite being the file meant to
carry data for the (still-stub) coordinator.

Patched by centralising the convention in `integration_hosts_storage.go`'s
`THostsEntityMaterialization.StateTopicTemplate` (+ a `StateTopic(hostName)` method), read by
both the automation generator and `generateCoordinatorDevicesFile`. But the user's reaction
("it worries me") was right to flag the deeper issue, not just this one instance.

**Why this matters:** re-reading Architecture.md §5 confirmed the *real* fix already exists on
paper — the **EventEndpoint** concept (identifier, state/command/availability topic, payload
converter, QoS, retain flag, direction, producer(s)/consumer(s)) — and §9's known-gap paragraph
already warns "don't grow more filename-keyed side-channel readers" against the target
`DSL → Semantic Model → {MQTT Generator, HA Generator, ...}` shape. `devices.yaml`'s ad hoc,
hand-grown fields (`capabilities`, `conceptual`, now `topic`) are exactly that kind of
pre-semantic-model side-channel — each addition is debt against the eventual EventEndpoint
model, not progress toward it. Architecture.md §9 now has this recorded as an explicit second
known gap (added 2026-08-20), alongside the original filename-driven-reads gap.

**How to apply:** it's fine to keep patching `devices.yaml` ad hoc *while the coordinator is
still a stub* — there's no real consumer forcing a proper model yet, and building one
speculatively would be premature (matches [[project-new-architecture-plan]]'s "shape via
experiments, don't over-engineer ahead of need"). But the moment the coordinator becomes a real
MQTT-connected process, that's the trigger to stop adding ad hoc fields and actually build the
EventEndpoint abstraction Architecture.md §5 already specifies, rather than letting
`devices.yaml` keep growing organically. Flag this if more `devices.yaml` fields get proposed
before that point.

**Update 2026-08-21 — the trigger has now fired.** User confirmed (via AskUserQuestion) they
want (a) the coordinator's first real version to do full MQTT discovery publishing, not just
connect+log, and (b) the EventEndpoint model built now rather than one more ad hoc field.
Before that design work started, though, `devices.yaml` grew further in the same ad hoc style —
topics renamed from `cpu/<host>/state`/`ping/<host>` to a shared `hosts/<host>/cpu/state` /
`hosts/<host>/node/state` convention (`THostsEntityMaterialization` gained
`NodeTopicTemplate`/`NodeTopic()` alongside `StateTopicTemplate`/`StateTopic()`), and three new
generated secrets files appeared: `coordinator/secrets.yaml`, `ping/secrets`, `cpu/secrets`
(all sourced from a new `resolveMQTTBrokerSecrets`/`TMQTTBrokerSecrets` in defined.go, reading
Settings.def's `${main_mqtt_server}`/`${main_mqtt_login}`/`${main_mqtt_password}`/`${main_mqtt_port}`
— renamed from the mismatched `${mqtt_*}` to match Physical.def's pre-existing `mqtt main:`
block, at the user's explicit request: "Settings.def should follow suit"). The
`integrationBodyParsers` dispatch signature was also consolidated into a `TPhysicalGenerationContext`
struct (Physical_Storage.go) since it had grown to 4+ positional parameters. None of this is
the EventEndpoint model itself — it's exactly the same category of ad hoc growth flagged above,
just more of it, landing right before the real design work. The actual EventEndpoint
abstraction + coordinator MQTT/discovery-publishing logic is still not started as of this note.
