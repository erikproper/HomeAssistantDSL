Built 2026-08-20, deployed and confirmed live 2026-08-21/22.

**Junglinster — done, running in production.** `Junglinster/deploy` (renamed from `update`)
rsyncs `hass/junglinster/`, `Integrations/cpu/`, `Integrations/ping/`, and
`~/go/src/homeassistant` + `Integrations/coordinator/` to protocols-server-1 (`ssh -p 1970`,
which since 2026-10-26 also distributes `Integrations/cpu/` to the other hosts -- xanadu, port
1969, did that until it became off by default), landing `coordinator/devices.yaml` +
`secrets.yaml` alongside `Integrations/coordinator/`'s `coordinator.service` +
`deploy.coordinator` on protocols-server-1. `deploy.coordinator` runs locally there: `go build`s
the coordinator, installs the binary to `/usr/local/bin` (not the source checkout under `$HOME` —
SELinux blocks systemd from exec'ing binaries there), installs/enables/restarts the
`coordinator.service` systemd unit. Confirmed via `journalctl`: service `active (running)`, real
`hosts/...` MQTT traffic flowing, HA discovery entities appearing with correct names/device
metadata.

**Vienna — still placeholder.** No target host provisioned yet; its `deploy.coordinator` still has
placeholder `COORD_HOST`/`COORD_USER`/`COORD_SERVICE` variables. Don't point it at a real host
speculatively.

**Vienna network issue (noted 2026-08-23):** a hardware (bridge/router) problem at the Vienna site
is currently blocking any cross-site data transfer testing between Junglinster and Vienna. This
sits on the critical path for PROJECT.md's roadmap step 2.6 ("enable cross-site MQTT") and for
Vienna's coordinator deployment generally -- don't expect to validate either until this is fixed.

**protocols-server-2 (added 2026-08-23/24).** A separate, pre-existing HA installation (Volvo,
Enphase Envoy, Netatmo, a printer, Bermuda BLE, EMS-ESP heater all already running there) — plain
Podman/quadlet container (`ghcr.io/home-assistant/home-assistant:stable`, `/etc/containers/systemd/
homeassistant.container`), NOT HAOS, host path `/var/lib/home-automation/homeassistant` mounted at
`/config:Z`. Now also gets generator output: `deploy.d/02_deploy.hass.protocols-server-2` rsyncs
`hass/protocols-server-2/` (configuration.yaml + integrations/automation.yaml + automation/ —
generated by `homeassistant/remote_instance_automations.go`) onto it directly via `root@` SSH on
port 1971. Two real bugs hit and fixed getting this live: (1) the deploy script's `ln -sf
automations.yaml automation/` step used the host's absolute path as the symlink target, which is
invisible from inside the container (different mount view) — HA's own error reporting then
misattributes the resulting failure to "File not found: /config/configuration.yaml" regardless of
which file actually broke; fixed by using a relative target (`../automations.yaml`) in both
`01_deploy.hass.junglinster` and `02_deploy.hass.protocols-server-2`. (2) current Home Assistant's
`mqtt.publish` service no longer accepts `payload_template` (schema validation error) — must
template `payload:` directly instead. Access: `erikp@protocols-server-2` over SSH, `sudo podman
exec -it homeassistant ...` for the container itself (system-level quadlet unit, not the user's own
rootless podman).

**Why:** part of [[project-mqtt-migration-plan]] — the coordinator will eventually co-locate with
the MQTT broker on a dedicated Fedora Pi4 for both houses; Junglinster's real host
(protocols-server-1) is already serving that role today even before such a dedicated Pi4 exists.

**How to apply:** Junglinster's deploy pipeline is a real, working, repeatable path — safe to
reference/reuse for redeploying after generator or coordinator code changes (e.g. after
`Integrations/cpu/report` changes, the deployed copy needs a fresh `./configure` + `deploy` run to
take effect). Vienna needs the same host-provisioning conversation before any deploy-script work
there is meaningful.
